## Goal
Every PR to `master` and every push to `master` of the public repo `MrKiirya/ha-energy-cost-stats` is checked
automatically on GitHub Actions. The checks are lint (ruff check + format check), lockfile freshness, pyright, and
all tests with the ≥ 95 % engine coverage gate. They run against both supported Home Assistant versions:
Python 3.13 → HA 2025.4.0 (minimum) and Python 3.14 → latest HA. A Windows job checks the native "no HA"
setup. `hassfest` and the HACS action validate the integration. Dependabot keeps the pinned actions current, and
a weekly canary warns when a new HA release breaks us. The README shows a CI badge. After the first green run,
a repository ruleset makes these checks required on `master`, requires PRs and blocks force-push. The main
session applies it manually, with human approval.

### Dependabot
- `github-actions` ecosystem: supported. It updates SHA pins and their `# vX.Y.Z` comments
  ([supported ecosystems](https://docs.github.com/en/code-security/dependabot/ecosystems-supported-by-dependabot/supported-ecosystems-and-repositories)).
- `uv` ecosystem: GA since 2025-03
  ([changelog](https://github.blog/changelog/2025-03-13-dependabot-version-updates-now-support-uv-in-general-availability/),
  [uv docs](https://docs.astral.sh/uv/guides/integration/dependabot/)). **Not enabled in this task**, because:
  1. It would try to bump the deliberate `==0.13.232` min-HA pin. `ignore` rules cannot be scoped to one
     `python_version` marker, so we would have to ignore PHCC entirely.
  2. PHCC is released daily and pins exact versions of pytest & co. Most tool bumps would be blocked by those pins
     or would conflict with them in the forked lock.
  3. It treats every dependency group as one bucket
     ([dependabot-core#13202](https://github.com/dependabot/dependabot-core/issues/13202)).
  See Open question 2.
- **How "latest HA" gets bumped (decision 5):** manually, on the light path.
  `uv lock --upgrade-package pytest-homeassistant-custom-component` updates only the 3.14 fork: the 3.13 fork is
  pinned `==` and cannot move. Then run `script/test` in the container, then open a `chore(deps):` PR. CI runs
  the new latest HA. The weekly **canary** workflow does that upgrade in CI without committing it, so we learn
  about a breaking HA release before we bump.

### Status-check names and the ruleset
- If a job has a `name:`, its check-run name is that name with any `${{ matrix.* }}` values filled in.
  Required status checks match on that string, so the job names below are **contract**. They are fixed here
  and in `.github/rulesets/master.json`, and a unit test enforces that the two agree.
- Ruleset API: `POST /repos/{owner}/{repo}/rulesets` with `name`, `target: branch`, `enforcement: active`,
  `conditions.ref_name.include: ["~DEFAULT_BRANCH"]`, and rules `deletion`, `non_fast_forward`,
  `pull_request`, `required_status_checks`
  ([REST — repository rules](https://docs.github.com/en/rest/repos/rules?apiVersion=2022-11-28)).
  `integration_id` pins each check to the GitHub Actions app (id `15368`). Step M2 checks this id against the
  real check runs before the ruleset is applied.

  on `run:` scripts). On Windows with Docker Desktop, from the repo root (PowerShell):
  `docker run --rm -v "${PWD}:/repo" --workdir /repo rhysd/actionlint:latest -color`
  ([actionlint usage](https://github.com/rhysd/actionlint/blob/main/docs/usage.md)). The image ships shellcheck.
- **The CI commands themselves**: the implementer runs the exact `run:` lines of the `test` job in the 001
  one-off containers (`ghcr.io/astral-sh/uv:python3.13-trixie` / `python3.14-trixie`, with
  `UV_PROJECT_ENVIRONMENT=/opt/venv UV_LINK_MODE=copy` and `<repo>` as a placeholder, never a real path).
  The `windows` job commands run natively in PowerShell.
- **`act`** is optional and is not an acceptance criterion. It cannot run the Windows job, and the
  docker-in-docker hassfest step is unreliable under it.
- **Verified only after the PR is opened** (by the main session / reviewer): actual job names and app id (M2),
  the setup-uv cache hit on the second run, the hassfest and HACS results, the badge rendering, and the Dependabot
  config being accepted (Insights → Dependency graph → Dependabot, or the first Dependabot run).

### Decisions (proposed; human may override in Open questions)
1. **Workflows.**
   - `ci.yml` covers the code: `lint`, `windows`, and the `test` matrix.
   - `validate.yml` covers the metadata: `hassfest` and `hacs`, plus a weekly schedule (upstream rules
     change without our commits).
   - `ha-latest-canary.yml` runs weekly and on manual dispatch. It is not a required check.
2. **Job names (= required check contexts)**:
   | Workflow | Job id | `name:` (check context) | Required |
   |---|---|---|---|
   | ci.yml | `lint` | `lint` | yes |
   | ci.yml | `windows` | `unit (windows, no HA)` | yes |
   | ci.yml | `test` | `test (py${{ matrix.python }}, HA ${{ matrix.ha }})` → `test (py3.13, HA 2025.4.0)`, `test (py3.14, HA latest)` | yes (both) |
   | validate.yml | `hassfest` | `hassfest` | yes |
   | validate.yml | `hacs` | `hacs` | yes |
   | ha-latest-canary.yml | `canary` | `canary (py3.14, HA upgraded)` | no |
3. **Pinning policy.** Code-executing third-party actions (`actions/checkout`, `astral-sh/setup-uv`) are pinned
   by full 40-char commit SHA plus a `# vX.Y.Z` comment, and Dependabot bumps them.
   `hacs/action@main` and `home-assistant/actions/hassfest@master` are the only allowed exceptions. Their docs
   recommend branch refs, their images float anyway, and validation must track current upstream rules. The
   exceptions are listed in one allowlist in the unit test, and each gets a YAML comment explaining why.
4. **No approvals required** in the ruleset (single maintainer). PRs are required, but the author can merge once
   checks are green. `strict_required_status_checks_policy: true` (the branch must be up to date).
   No bypass actors (see Open question 3).
5. **Latest-HA bump is manual** (light path), with the canary as an early warning. No Dependabot `uv` for now.
6. **Card job**: not in this task. `ci.yml` gets a comment `# Card (frontend/) job: added in roadmap stage 4.`
7. **PyYAML in `dev`** (`pyyaml>=6`, loose bound, because HA pins an exact PyYAML in the `ha` fork). The CI config
   unit tests need it. Add `types-PyYAML` only if pyright reports missing stubs for `tests/`.
   `uv lock --check` must still pass.

### Workflow content spec (the implementer writes the YAML; this is the required behaviour)
Common to all workflows:
- top-level `permissions: contents: read` (or `{}` for `validate.yml` if the HACS token still works; implementer's
  choice, documented in Implementation notes). No `pull_request_target`, no secrets beyond `GITHUB_TOKEN`.
- `concurrency: { group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true }` on ci/validate.
- every job has `timeout-minutes` (e.g. 20; canary 30) and `runs-on: ubuntu-latest` except `windows`
  (`windows-latest`).
- setup-uv with `enable-cache: true`. Env `UV_PYTHON_PREFERENCE: only-managed`, so uv downloads the latest
  patch of the requested Python and does not use a runner's system 3.14.0/3.14.1 (which would miss the
  `>=3.14.2` marker). Env `UV_LOCKED: "1"` in `ci.yml`, so every `uv sync`/`uv run` fails if `uv.lock` is stale.
  The canary does **not** set it.

`ci.yml` — triggers: `pull_request` (branches `[master]`), `push` (branches `[master]`), `workflow_dispatch`.
- `lint`: checkout → setup-uv (python `3.14`) → `uv sync` → `uv lock --check` → `sh script/lint`.
- `windows`: checkout → setup-uv (python `3.14`) → `uv sync` → `uv run pytest -m unit` → an integration-guard
  step in `pwsh`: `uv run pytest -m integration`, require `$LASTEXITCODE -eq 5`, then `exit 0`.
  GitHub's pwsh wrapper otherwise fails the step on the non-zero exit code. This proves the native no-HA setup
  still collects cleanly.
- `test`: `strategy.fail-fast: false`; matrix `include: [{python: "3.13", ha: "2025.4.0"}, {python: "3.14", ha: "latest"}]`.
  Steps: checkout → setup-uv (`python-version: ${{ matrix.python }}`) → `sh script/setup` →
  **Assert HA version**: `uv run --group ha python -c "import homeassistant.const as c; print(c.__version__)"`.
  The step fails if the import fails, and when `matrix.ha != 'latest'` it also fails if the printed version
  ≠ `matrix.ha`. The printed version goes to `$GITHUB_STEP_SUMMARY`.
  Then → `uv run --group ha pyright` → `sh script/test`. The coverage gate lives in `script/test`, so it runs
  on both legs.
  Note: running the scripts with `sh script/…` does not depend on the executable bit (see 001).
- The comment about the card job (decision 6).

`validate.yml` — triggers: `pull_request` (`[master]`), `push` (`[master]`), `schedule` weekly (e.g.
`"0 4 * * 1"`), `workflow_dispatch`.
- `hassfest`: checkout → `home-assistant/actions/hassfest@master`.
- `hacs`: `hacs/action@main` with `category: integration`, `ignore: brands` (comment: "no brand/icon.png yet — see
  follow-up in tasks/003-ci.md"), `comment: "false"` (no PR comments, so no `pull-requests: write` is needed).

`ha-latest-canary.yml` — triggers: `schedule` weekly (e.g. `"0 5 * * 1"`), `workflow_dispatch`.
- `canary`: checkout → setup-uv (python `3.14`) →
  `uv lock --upgrade-package pytest-homeassistant-custom-component` → `sh script/setup` → print the HA version
  to the step summary → `uv run --group ha pyright` → `sh script/test`. Nothing is committed. A failure means
  "the next HA release breaks us; open a fix task before bumping".

`.github/dependabot.yml`: `version: 2`, one `github-actions` entry (`directory: "/"`, weekly schedule, one
`groups` entry matching `"*"` so all action bumps arrive in one PR, `commit-message.prefix: "ci"`).

`.github/rulesets/master.json` — the exact request body for step M2 (commit it, so the setting is reviewable
and reproducible):
